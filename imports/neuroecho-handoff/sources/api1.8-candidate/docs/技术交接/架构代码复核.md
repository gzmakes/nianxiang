# 念响多端与架构只读审查

审查时间：2026-10-30。权威源码：`outputs/念响-本机原型`。下述行号为本次读取时的源码快照；本轮有共享契约工具在并行补充，后续行号可能移动。

没有读取真实 `data.db`、模型配置、CLI 凭据或钥匙串；没有发起外网访问，没有修改产品代码。

## 结论

当前适合称为“同一产品的 Web/H5/macOS 可运行原型 + iOS/Android 原生开发起点”，不能称为“各端已完成上线与跨设备同步”。原生端源码已实现 API 路径，不等于完成 iOS/Android SDK 构建、签名、安装、真机和网络验收。

保留 FastAPI + SQLite + Electron + SwiftUI + Compose。先统一设计/文案/行为和 API 契约，再补多设备状态一致性，最后单独建设远程鉴权和设备配对。不建议为“同步”立即重写所有客户端或拆微服务。

## P0：真机远程使用之前的硬门槛

### P0-1 远程服务与用户/设备身份尚未实现——未来能力，不是当前本机故障

**事实：** `server/main.py:55–57` 明确说明本机 native 无 Origin 请求可用，规则不认证本机进程；70–78 行仅接受 loopback Host/peer。iOS 默认 `127.0.0.1:18787`（`native/ios/App/EchoStore.swift:18–22`），网络客户端没有用户鉴权头（`native/ios/Sources/EchoCore/APIClient.swift:40–46`）；Android 同样仅设置 JSON 头（`native/android/app/src/main/java/cn/xinji/echo/Api.kt:34–45`）。

**影响：** 手机设置里能填写 HTTPS 地址，不代表当前已有远程后端。直接改成 `0.0.0.0` 或加一个公网反向代理，会把个人模型与 CLI 执行能力放到不合适的安全边界之外，而且现有 Host guard 本来就会拒绝这种请求。

**渐进方案：** 比赛前继续本机与模拟器/USB 联调。准备真机无线/多人试用时，另建受保护服务入口：身份认证、设备配对和撤销、每用户/设备授权、限流及审计，再验证真机可达。Mac CLI、AppleScript、本地文件与脑电读取留在 Mac 本地 agent，远程端只能提交白名单能力请求，不接受任意 shell/本机路径。不要为联调去掉现有 Origin/Host 检查。

**验收：** 未配对设备不能获取对话、来源或模型调用；撤销设备后立即失效；失败/重放请求不触发第二次系统写入；手机离开 Mac 后功能边界如实展示。

### P0-2 原生安装与运行尚待开发同学完成——已确认交付边界

**事实：** iOS README 7–20、81 行明确没有 iOS SDK 构建/安装/签名/真机证明；Android README 5、14、69–79 行明确没有 APK/Android 运行验收。宿主 Swift、纯 JVM 与合成契约测试有价值，但不能替代 SwiftUI/Compose 在目标平台的构建和 UI 验收。

**交接要求：** 每端代码包带同一后端版本、设计版本、API 快照、启动说明、已验收/未验收列表和 5 条主流程。先让开发同学产生可安装 Debug 包，再进入“打磨”；不要把设备连通或 SDK 编译当成只剩视觉微调。

## P1：多人维护与两台设备联调前优先补齐

### P1-1 视觉/偏好/文案是三份手写，已出现默认值差异——已确认现状

**证据：** Web `web/design-system.js:3–4` 默认 `false/false/.7`；iOS `native/ios/App/Design.swift:11–12,62–63` 默认减少动态 `false`、光强 `.65`，降低透明度主要服从系统；Android `EchoViewModel.kt:19,25` 默认 `true/true/.45`。颜色分别写在 `web/design-system.css:2`、`native/ios/App/Design.swift:3–7,18` 与 Android `MainActivity.kt:49–55,105`；Web 与 H5 仍各有 `app.js`（2741 行）和 `m.js`（1920 行）的流程/文案。平台差异可以是刻意选择，但当前没有机器可核对的差异声明。

**建议：** 单仓库保留各平台原生 UI，新增版本化 `shared/design/tokens.json`、`shared/copy/zh-CN.json`、`shared/product/behavior.json`。tokens 生成 CSS variables、Swift 常量、Kotlin 常量；关键文案使用同一 ID；行为清单固定“一个主对话、草稿不自动发送、来源先预览再确认、unknown 只核对”等规则。字体/导航/触控尺寸允许在 platform overrides 里明确覆盖。已有用户偏好不因统一默认值被重置。

**验收：** 修改一个 token 后生成物出现三个平台 diff；修改关键文案后不存在旧版本；CI 用 `--check` 拒绝未重新生成的产物。每次需求变更由同一变更单列出 Web/H5/macOS/iOS/Android 的适用/不适用/待完成状态，不靠口头“都跟一下”。

### P1-2 有同一个数据源，没有实时多设备同步协议——已确认能力缺口

**证据：** `core.py:266` 是 per DB canonical，不是 account/device identity。`GET /api/conversation` 返回 session/messages/memories/bookmark/context（`main.py:649–654`），没有全局 revision/cursor/删除事件。Web/H5 在 restore 时读取该接口（`web/app.js:2562–2570`、`web/m.js:1853–1858`）；iOS `EchoStore.swift:48–57`、Android `EchoViewModel.kt:58–65` 为显式刷新/操作后的快照读取。未发现对话变更流或跨客户端消息广播。Web 的 `storage` 事件只是本浏览器 origin 内显示偏好，不跨原生设备（`design-system.js:18–20`）。

**建议：** 第一阶段明确“连同一服务并刷新即可读同一数据”，增加回前台刷新与可见的最后刷新状态；随后增加服务端单调 `conversation_revision`，`GET changes?after=cursor` 返回增量和 tombstones（删除/撤回），客户端只缓存服务端事实。先用有节制的前台拉取或 SSE；没有复杂双向实时需求就不先引入 WebSocket。离线只保留草稿和待核对请求，先不做离线自动合并。

**验收：** A 发消息/B 刷新后看到；A 删除记忆/B 不再拿旧卡确认；来源撤回两端都停止使用；后台恢复不重发；版本不兼容给出可操作提示。

### P1-3 记忆 version 没有作为更新前置条件；跨端并发策略不完整——风险，由代码结构确认

**证据：** Memory 有 version/history（`core.py:63–74,575–605`），但 `MemoryPatch` 只有 text/status（`main.py:114–116`），调用不传 expected version（iOS `APIClient.swift:96–98`、Android `EchoViewModel.kt:133–135`）；服务端按照当时数据库内容递增，不拒绝陈旧客户端。两端同时编辑同卡时存在后写覆盖先写的风险。聊天 ledger 以 request ID 去重（`chat_turns.py:97–108,121–134`），并不规定同一 conversation 的两个不同请求的先后顺序；模型上下文戳仅含 session/memories/sources（`core.py:1075–1083`），不含消息游标。未运行并发真机复现，不能称为已观察到的数据丢失。

**建议：** 更新/删除记忆加入 `expected_version`，事务内条件更新，冲突返回 `409` 与当前版本，UI 让用户重新核对；不静默覆盖。聊天选择一个明确策略：初期同一 conversation 只允许一个服务端在途轮次，其它端读到正在回应并可继续保留草稿；或加入 conversation sequence 与明确 supersede 规则。request ID 保持现有重试语义。来源 attach/create action 在未来远程重试场景补 idempotency key，不能只靠客户端 busy。

**验收：** A/B 都读 v1，A 成功写 v2，B 改 v1 返回冲突且草稿保留；两个不同设备同时发送可解释排序；断网恢复不重复消息/动作；删除/撤回与正在生成的回复并发时继续保持现有弃权保证。

### P1-4 已有 OpenAPI 快照仍欠响应/行为契约——已确认缺口，本轮部分补齐中

**证据：** 本轮已新增 `scripts/export_api_contract.py:1–21` 与 `shared/api/openapi.json`，支持不启动服务导出/校验声明。这是正确起点。静态读取快照发现 `/api/conversation`、`/api/chat`、`/api/memory/{mid}`、`/api/actions` 的成功响应 schema 为 `{}`；原因是路由大多返回 dict 且没有 response_model（如 `main.py:649–654,748–787,840–845,1034–1036`）。iOS Codable、Android JSONObject 手写解码分别见 `Models.swift` 与 `Api.kt:16–29`。版本目前 FastAPI health 为 0.1.0，桌面 package 为 0.2.0，不能据此判断兼容性。

**建议：** 为核心 5 个域补 Pydantic 输出模型和稳定的错误码（保留本地化 message），先固定 conversation/turn/memory/source/action 的枚举和必要字段。维护一个 `contract_version`，增加兼容能力字段而不是依赖 app 包版本。源 schema → 生成/校验 DTO；复杂状态逻辑不强行代码生成。共享合成 fixtures 覆盖 202/409/429/unknown/撤回/版本冲突，Swift/Kotlin/JS 解码同一套输入。把生成物漂移、客户端规则、服务端测试与真实平台构建放入 CI，标明缺 SDK 时的 not run，不能当 pass。

**验收：** 只删除/改名一个 response 字段会在客户端合约检查失败；兼容增加字段不破坏旧客户端；错误码驱动行为，不靠中英文提示字符串判断。

## P2：随下一轮迭代分层，避免一次重写

### P2-1 后端做模块化单体，平台 adapter 保持隔离——维护建议

**证据：** `server/core.py` 1727 行，含 schema/migration、记忆、来源、聊天编排、合成设备、系统动作；`main.py` 1095 行，含 HTTP schema、预览缓存/定时器、MindLink grant、路由和页面/下载路由。已有 `model.py`、`source_context.py`、`chat_turns.py`、独立 connector 文件，是可以继续拆分的基础。

**建议目录：** `api/routers + api/schemas` 负责 HTTP；`services/conversation,memory,sources,actions` 负责用例与事务；`repositories/sqlite` 负责 SQL/migration；`adapters/model,feishu,notion,apple,mindlink,rokid` 负责外部边界。一次只迁移一个域并运行现有回归；保留同一进程和 SQLite。数据库先加有版本号的迁移和备份恢复检查，多用户/写入规模真的需要时再换 PostgreSQL。

### P2-2 电脑执行能力和硬件不能随云端服务搬走——边界建议

**证据：** Mac Apple 连接器使用 osascript（`apple_source.py:42–85`），飞书使用宿主 lark-cli（`lark.py:20–22,73,114`），Notion 使用已有 CLI（`notion_cli_source.py:51–60`）。MindLink 读取固定本机 8876，校验 live/信号质量/时效且不解码情绪（`mindlink.py:1–5,14–18,52–82`）；授权 token 仅进程内 TTL（`main.py:891–938`）。`device_bridge.py:1–7,27–77` 明确是 synthetic，不是 Rokid 已接通。

**建议：** 保留 `capabilities` 矩阵：可用、需条件、未授权、当前设备不支持、待联调。手机日历与 Mac 日历用不同 adapter/target 显示；不把“读 Mac 日历”当成“读本机手机日历”。未来 local agent 由用户显式配对，凭据留设备侧；Rokid 只做低打扰呈现与显式输入，EEG 只当可丢弃的专注反馈，不默认进入长期记忆或情绪标签。设备信号与聊天/系统动作的业务状态分开，不让光球状态成为脑电测量结果。

**进程边界：** 当前预览、MindLink grant 等在进程内，chat lease 又声明单 worker（`chat_turns.py:83–88`）；现阶段这是合理限制。若将来多 worker，先迁移 preview/grant/turn 协调状态并重新设计 worker lease，不能直接 `--workers 4`。

## 推荐交付与协作节奏

1. **本次交接**：源码 + 同版本设计与 API/行为快照 + 构建说明 + 平台矩阵；注明 SDK/真机未验收。指定一份仓库为唯一权威，避免多个 zip 分别继续改。
2. **开发同学首个里程碑**：iOS/Android 可安装 Debug 包，完成唯一对话/真实回复、资料预览确认、记忆纠正撤回、unknown 恢复五条主流程；每端录一段验收，不以静态测试代替。
3. **下一迭代**：补齐 response contracts、共享默认值、expected_version、foreground refresh/revision；同时补平台 CI。再决定受保护的远程服务和设备配对方案。

## 此时不建议做

- 不改成微服务、Kafka、多代理平台；现阶段单体事务和已有回归更有价值。
- 不为避免多端文案差异把原生客户端全部重写成 WebView/Flutter/React Native；先共享数据/规则/设计资产，保留原生体验。
- 不用“远程配置”动态替换安全确认或在审核之外改变执行权限；配置只适合已知 token/文案/能力显示，行为变更随版本发布。
- 不复制 SQLite 文件充当多设备同步，不各端维护一条互不相干的“唯一对话”，不做整段聊天自动离线合并。
- 不为展示完整而补假提醒、假 Rokid ACK、情绪解码或已完成标签；未实现/未验收能力继续如实标明。
