# 回响多端一致性只读审计

核对日期：2026-10-30。范围：`outputs/念响-本机原型` 当前源码。先只读核对，不读取凭据、用户数据库，不联网，不重跑原生编译；随后按 root 指令仅修复 Web 文件 Unicode 截断，并运行受影响的纯 JS 测试。本报告描述源码中可确认的实现；不以源码存在代替 iOS / Android 安装、签名或真机验收。

## 判断

已经有 Web / H5 / Electron / SwiftUI / Compose 五个界面入口，并有共用后端和持续对话接口；**尚未达到功能、文案、状态与默认设置完全一致**。Web 和 H5 已共用部分 JavaScript 组件；原生端主要依据同一规范分别手写，仍会漂移。优先建立版本化共享契约，保留原生呈现与系统能力差异；当前阶段不建议为追求完全同一份 UI 而重写成跨端框架。

## 实际范围规则

1. **本地文本：**三端都限制 1–3 份，UTF-8，单份最多 256 × 1024 bytes；扩展名均为 md / markdown / txt / json / py / ts / js / csv；预览并明确确认之后才上传和接入。iOS、Android 按 Unicode 标量 / 码点截前 4000；本次已将 Web 的 UTF-16 字符单元截断修正为码点截断，见下方修复记录。
2. **飞书：**三端均为指定一篇、后端读取、最多保留 12000 字、预览非全文。Web / H5 文案完整描述“每来源最多 3 段、全对话最多 8 段 / 3200 字”；Android 飞书同样披露；iOS 仅描述“必要内容可能发送”，没有相同数字边界。真实检索限制由 `server/core.py:418–441` 执行，客户端不应复制算法。
3. **Notion：**iOS 支持复用后端 ntn CLI、单页前 50 个顶层文本块；Web / H5 还有 token 方式；Android 暂未开放这类操作。是否开放必须由能力表而非客户端从后端 `ready` 自行推定。
4. **Mac 资源：**日历、提醒、Git 来源由服务所在 Mac 读取，不能将其描述成手机日历 / 手机文件系统。iOS 明确写出运行位置；Android 总说明已写后端所在电脑，但卡片 `ready` 文案尚未区分“后端 ready / 此端实现”。
5. **撤回：**逐来源移除会清理对应派生记忆，其他来源 / 聊天保留，并不撤销第三方账号授权。删除记忆还可能将有明确出处的关联来源标为 stale，防止从原文重新得出被忘掉的内容；各端应统一解释这个关联影响。
6. **写入：**Web / Electron 能在额外明确勾选时请求后端写入 Mac 日历或提醒；原生端始终 `real:false`。手机系统写入、远程认证、EEG / Rokid 真机尚不在已完成范围。

## 真实问题与精确定位

P2 表示功能打磨前应处理；P3 表示允许以明确能力差异交接。此审计没有发现需要直接阻断本机已有 Web / Electron 使用的 P0。

1. **P2 已修复：Web 文件截断可能生成半个 surrogate，导致接入失败。** 原 `web/file-picker.js:25` 使用 `content.slice(0,4000)`；输入 3999 个 ASCII + 一个 😀，截断落在 UTF-16 代理项中间。现改为 `Array.from(content)` 后按码点截断与判断 truncated，与 iOS `Models.swift:163`、Android `Rules.kt:39–40` 一致。新增四个纯 JS 回归测试：emoji 恰好第 4000 位、emoji 在第 4001 位、中文、空 / 空白输入。受影响测试 **8/8**、完整前端 **330/330** 通过，日志 `work/consistency-handoff-js.log`。备份在 `work/backup-before-consistency-handoff/web/file-picker.js` 与 `tests/test_file_picker.js`。未改 server / 原生，未向真实用户服务发合成请求。后续另可补后端畸形 Unicode 返回受控 400 的防御；这不属于本次客户端截断修复。
2. **P2：Android 来源卡片会说“后端可读取”，但该端按钮永久禁用。** `MainActivity.kt:273` 按 descriptor ready 显示可读取；`:145` 只放行 local_files、飞书 ready、Apple 日历 ready。iOS 的 `ConnectionViews.swift:83` 另支持 notion / git / github / apple_reminders，Web 更多。建议显式组合 `backend_status × client_implemented × permission_state`，未实现显示“此端尚未开放”，不能把缺功能归因于账号或权限。
3. **P2：Android 忘记确认没有说明关联来源会暂停。** `MainActivity.kt:130` 说其他资料保留；后端 `core.py:545–563,566–572` 会将有出处的关联来源设 stale。数据仍保留但用途改变，用户可能以为只有一条记忆停止使用。iOS `MemoryViews.swift:36` 已说明相关来源可能暂停。建议使用共同危险操作说明，清楚分开“保留内容”和“暂停用于回复”。
4. **P2：原生状态光与真实处理状态未绑定。** iOS `Design.swift:59–71`、Android `MainActivity.kt:176–179` 没有接受真实状态参数；读写或发送过程中仍描述安静。iOS `RootViews.swift:24` 和 Android `MainActivity.kt:96` 的顶部文字只用 pending 二分。应共用状态枚举和映射，不用动画推断业务结果。
5. **P2：Android 记忆模型丢失结构化出处。** `Api.kt:17,22` 未保留 `source_message_id` / `source_attachment_id`，界面 `MainActivity.kt:292` 把 `memory.source` 文本放在“说于”字段中；它是来源描述，非时间。iOS `Models.swift:21–24` 保留这些字段，`MemoryViews.swift:38` 可回查原消息时间。建议结构化字段齐全，缺时间则写“原话时间未记录”。
6. **P3：iOS 减少动态不约束聊天自动滚动动画。** `RootViews.swift:95` 固定 `withAnimation`，而 `Design.swift` 已遵循系统与 App 减少动态。需要将自动滚动也映射同一 effectiveReduceMotion。此处仅静态发现，具体辅助设置体验仍需真机。
7. **P3：搜索、话题、原话留存、新建记忆能力有差异。** `web/design-system.js:23–35` 搜索消息+记忆并维护话题；iOS `RootViews.swift:90,119–125` 只复制 / 搜消息；Android `MainActivity.kt:204–225` 搜消息并允许留存。可以按阶段上线，但交接必须标注，不称各端功能完成。

## 最值得统一的五条

1. **共享能力与范围契约。** 建 `capabilities.json` / 对应 endpoint，标明每端 implemented、backend ready、read scope、preview required、device owner、真实写入边界。范围数字只在服务端定义并提供版本，所有客户端渲染同一承诺。
2. **共享机器可读 design tokens。** 一份源生成 CSS / Swift / Kotlin 变量，包含 semantic userBubble / card / ink / lightIntensity 默认。字体角色、触控目标与材质采用显式平台覆盖；不强求三个平台完全相同的像素与玻璃实现。
3. **共享关键文案目录。** 以语义键管理导航、确认、来源、记忆、错误、pending、stale，而不是复制整个页面句子。操作说明尤其要写明 backend / 当前设备，确认后是否会发送模型服务，删除是否让关联来源暂停。危险文案不能各端自由翻译。
4. **共享 API schema + 状态机。** 从 OpenAPI 固化 Conversation / Message / Memory / Source / Action / PendingTurn；保留 provenance、timestamps、real、receipt。定义 client request ID、preview consumed/expired、unknown/check-only、cancel wanted/server confirmed，并用同一合成 fixtures 验证三端。渲染层仍为 SwiftUI / Compose / DOM。
5. **共享发布验收矩阵。** 任何调整必须列明受影响端、版本与是否同步；至少覆盖进入同一对话、连续聊天、预览/确认/撤回、记忆纠正/忘记、unknown不重发、缩放/降低动态。以 source → generator → fixture contract → 各端构建/真机签收为流程；不把一个端截图变更当作全端完成。

## 应共用与应保留差异

| 应共用 | 应保留平台差异 |
|---|---|
| 产品实体 / DTO、状态枚举、失败语义、用户范围承诺 | UIKit / SwiftUI 与 M3 原生控件、返回手势、文件选择器 |
| 单条对话 ID、记忆和出处、源是否 stale、任务真实结果 | CSS px / pt / dp、44 / 48 触控目标、动态字体实现 |
| 颜色语义和字号角色、关键文案、确认/拒绝语义 | Liquid Glass / Web backdrop / Android 不透明降级 |
| 能力表、授权范围、客户端最低协议版本 | Mac 托盘 / 全局快捷键；手机通知与系统权限须独立实现 |
| 共享 fixtures、范围边界、破坏性操作解释 | 减少动态/透明度的系统优先；偏好是否跨设备同步需产品明确选择 |

建议下一阶段架构方向：同仓库 `shared/` 契约 + `server/` 权威业务规则 + `web/desktop/native/` 平台适配层即可。先做可生成且能被检查的共享源，不为本次黑客松引入完整微服务、远程动态布局或通用跨端 UI 框架。
